# Service Order Quote Pricing Design

## Goal

Move service-order surcharges and discounts out of dedicated database columns and into
`ServiceOrder.quote`. Keep VAT as explicit fields on `ServiceOrder`. The estimated-price and create
flows must use the same backend-owned pricing rules and must not trust client-calculated prices.

## Canonical Pricing Contract

`IQuoteItem[]` is the source of truth for all non-VAT price adjustments:

| Item | `code` | `type` |
| --- | --- | --- |
| Base service fee or manual quote line | `null` | `inc` or `dec` |
| Urgent-order surcharge | `URGENT` | `inc` |
| Fragile-item surcharge | `FRAGILE_ITEM` | `inc` |
| Voucher discount | `VOUCHER_DISCOUNT` | `dec` |
| Points discount | `POINTS_DISCOUNT` | Reserved; not currently generated |

Each item contains `key`, non-negative `value`, `code`, `type`, and optional `note`.

- `basePrice` is the sum of base service-fee lines before surcharges and discounts.
- `preVatAmount` is the signed quote total, clamped to zero.
- `vatAmount = preVatAmount * vat / 100` when `hasVat` is true.
- `amount = preVatAmount + vatAmount`.
- VAT is never added to `quote`.

The following removed model fields must also be removed from validators, selects, services, tests,
and dependent mappings: `urgentSurchargePercent`, `urgentSurchargeAmount`,
`fragileItemSurchargePercent`, `fragileItemSurchargeAmount`, `isUsePoints`, `usedPoints`,
`pointsDiscountAmount`, `voucherDiscountAmount`, and `discountedPrice`.

## Pricing Rules

The backend reads `AppSetting.order` for every estimate or recalculation.

Urgent pricing applies only when `urgentOrderEnabled` is true and the scheduled time is in the
window `0 <= timeAt - now <= urgentOrderHours`. The backend owns `isUrgent`; client-provided values
are ignored or rejected. The urgent surcharge equals `basePrice * urgentOrderSurchargePercent / 100`.

Fragile pricing applies when the customer selects `hasFragileItems`. The surcharge equals
`basePrice * fragileItemSurchargePercent / 100`.

Voucher discount is resolved from the customer's valid voucher after both surcharges. Its applied
value cannot exceed the subtotal before VAT. Points pricing is out of scope and the enum value is
kept only for contract compatibility.

When recalculating, the backend removes existing backend-managed quote codes (`URGENT`,
`FRAGILE_ITEM`, `VOUCHER_DISCOUNT`, and `POINTS_DISCOUNT`) and regenerates the applicable rows.
Manual rows with `code: null` are preserved. This prevents duplicate or client-forged managed fees.

## API Data Flow

### Estimated Price

`POST /v1/client/service-orders/estimated-price` adds `hasFragileItems` to its request. It remains
available only for `Service.autoQuote = true`, requires at least one valid
`servicePrices: [{ servicePriceId, quantity }]`, and resolves every price from the database.

The response is:

```ts
{
  items: IQuoteItem[];
  basePrice: number;
  preVatAmount: number;
  vat: number;
  vatAmount: number;
  totalPrice: number;
  isUrgent: boolean;
}
```

`items` excludes VAT.

### Create Service Order

Automatic-price creation requires `serviceId` and at least one
`servicePrices: [{ servicePriceId, quantity }]`. The backend validates ownership of each price row,
loads current database prices, calculates the quote again, and stores a service-price snapshot.
Client-supplied `quote`, totals, surcharges, discounts, VAT amounts, and `isUrgent` are not trusted.

Manual-price creation still requires `serviceId`, accepts `servicePrices: null | []`, sets
`needsQuote = true`, and leaves `quote` and calculated totals empty until an administrator supplies
manual quote lines. A request item with `servicePriceId: null` is not supported; absence is
represented by `null` or an empty array.

### Update and Confirmation

Changing `timeAt`, `hasFragileItems`, `vouchersId`, or `hasVat` triggers recalculation. Admin-entered
manual quote rows are retained, while managed quote-code rows are regenerated by the backend.

When confirming a `ServiceOrder` into an `Order`, `discountAmount` is the sum of quote rows with
`type: "dec"`. `Order.details` contains only rows with `type: "inc"`, preventing discount rows from
becoming positive order costs.

## Validation and Errors

- Create and update schemas remove all deleted model fields.
- Quote schemas validate `key`, `value >= 0`, `code`, `type`, and optional `note`.
- Estimated-price rejects manual services and empty/invalid automatic price selections.
- Automatic create rejects service-price rows that do not belong to `serviceId`.
- Manual create accepts only `servicePrices: null | []`.
- Missing AppSetting disables urgent pricing and uses zero for absent surcharge percentages.
- Existing voucher ownership, unused-state, and expiry checks remain mandatory.

## Persistence and Migration

`ServiceOrder` continues to persist `basePrice`, `quote`, `preVatAmount`, `hasVat`, `vat`,
`vatAmount`, and `amount`. If the removed columns exist in deployed databases, add a guarded
migration to drop them. The migration must not alter VAT columns or `vouchersId`.

## Verification

Focused tests must cover:

- urgent enablement, disabled state, future-time boundary, and expired scheduled time;
- fragile surcharge based on base service price;
- simultaneous urgent and fragile surcharges;
- voucher application after surcharges and clamping at zero;
- VAT excluded from quote and returned/stored separately;
- signed quote totals and managed-code deduplication;
- identical estimate and create results for identical trusted inputs;
- automatic create ignoring client-calculated fields;
- manual create without service-price rows;
- update-triggered recalculation;
- confirmation mapping discounts and increment rows correctly.

Run focused Jest specs, the backend build, and a literal stale-reference scan for every removed field.
Update `src/modules/serviceOrder/SKILL.md` with the final pricing invariants after implementation.
